# 构建工具（Build & Engineering）

> 本文档用于定义 **现代 Android / KMP 项目中的构建工程（Build Engineering）选型与治理方案**。  
> 构建工具不直接影响业务功能，但**决定项目的可维护性、构建性能和团队协作效率**。

---

## 为什么需要“构建工具”这一维度？

在早期 Android 项目中，技术选型主要关注：
- 网络库
- 存储方案
- UI 框架

但在 **中大型、多模块、长期维护** 的项目中，真正的瓶颈往往来自：

- Gradle 配置分散、重复
- 模块数量增加导致构建时间失控
- 依赖冗余、隐式依赖无人治理
- CI 构建越来越慢，但无人敢优化

> **现代 Android 开发 = Runtime 技术 + Build Engineering 能力**

因此，构建工具必须作为 **一级技术维度** 单独对待。

---

## 构建工具的核心目标

构建工程并不是“让 Gradle 更复杂”，而是解决三类问题：

1. **配置一致性**：避免多模块 Gradle 配置混乱
2. **依赖可控性**：防止依赖失控、模块耦合
3. **构建性能可观测**：发现并治理构建退化


构建工具可以清晰地分为两大类：

Build & Engineering
├── 配置规范化（Convention & Standardization）
└── 构建分析与治理（Analysis & Governance）

## 构建治理决策建议

为了将上述工具落地，建议按照以下阶段进行构建治理：

### 阶段一：声明式治理（0 -> 1）
*   **强制引入 Version Catalogs (`libs.toml`)**：废弃 `Dependencies.kt` 或全局 `ext` 变量，确保所有模块共用同一份版本清单。
*   **统一 Gradle 脚本语言**：全量使用 **Kotlin DSL (.gradle.kts)**，废弃 Groovy，实现“构建脚本即代码”。

### 阶段二：配置标准化（1 -> N）
*   **引入 Convention Plugins**：将通用的 `android` 块配置（compileSdk, MinSdk, 混淆规则, 编译器参数）封装成插件（如 `com.your.app.android.library`）。
*   **模块化解耦**：禁止使用 `allprojects { ... }`，所有模块通过引入 Convention Plugin “声明式”地获取配置。

### 阶段三：可观测性与性能优化（治理期）
*   **构建耗时基准测试**：每周通过 `gradle-profiler` 或 **Build Scan** 生成报告，监控构建时间波动。
*   **依赖合规性检查**：通过 Gradle Task 自动扫描重复依赖、隐式依赖以及不合规的协议（License）。


## 构建工具选型决策树

1. **项目刚起步？** 
   - 必须使用 **Version Catalogs** 管理依赖。
   - 使用 **Kotlin DSL** 编写 Gradle 脚本。

2. **模块超过 10 个？** 
   - 必须引入 **Convention Plugins** 提取公共配置（Java 版本、编译器参数、基础依赖）。

3. **构建时间超过 5 分钟？** 
   - 必须引入 **Gradle Build Scan** 定位耗时任务。
   - 考虑配置 **Remote Build Cache**。

4. **KMP 项目？**
   - 严格遵循 **Standard Tooling**，避免在 Gradle 中写过多的 Native 相关硬编码逻辑。
