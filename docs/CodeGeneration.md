# 代码生成（Code Generation）技术对比选型表

| 技术方案 | 核心定位 | 状态 | 跨平台 (KMP) | 构建影响 (全量/增量) | 实现原理 | 接入难度 | 调试友好度 | 优点 | 缺点 | 选型建议 |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---|:---|:---|
| **KSP (Kotlin Symbol Processing)** | **现代代码生成首选** | 🔥 核心 | ✅ **原生支持** | 中 / 优 | 直接分析 Kotlin 语法树 | 中 | 优 | 比 KAPT 快 2x，原生支持 KMP，Google/JetBrains 强推 | 需理解 Kotlin 符号模型 | **所有新项目、KMP 项目的代码生成首选** |
| **KAPT (Annotation Processing)** | **Java 遗产/兼容方案** | ⚠️ 过时 | ❌ (仅限 JVM) | **高 / 差** | 生成 Java Stub 进行处理 | 低 | 中 | 兼容所有 Java APT 库（如 Dagger/DataBinding） | **显著拖慢编译速度**，不支持 KMP，处于维护期 | **仅用于维护重度依赖旧 Java 库的项目** |
| **Kotlin Compiler Plugin** | **底层语言增强** | 🚀 进阶 | ✅ **原生支持** | 高 / 中 | 拦截并修改编译器 IR | **极高** | 极差 | 无需生成源码文件，可改变语言行为（如 Compose/Serialization） | 开发成本极高，API 不稳定，维护难 | **仅限框架开发者或有特殊语言增强需求时使用** |
| **KotlinPoet** | **源码生成辅助工具** | 📦 基础 | ✅ 支持 | - | 声明式生成 .kt 代码 | 低 | 优 | 生成的代码美观、类型安全，防止字符串拼接错误 | 只是工具，需配合 KSP/KAPT 使用 | **编写自定义 CodeGen 插件时的标准工具** |
| **Gradle Task (Scripting)** | **简单资源/配置生成** | ⭐ 主流 | ✅ 支持 | 低 / 优 | Task 读取并输出文件 | 低 | 中 | 灵活度极高，适合生成 BuildConfig、版本号、资源列表 | 缺乏对代码语法结构的深度感知 | **生成简单常量、资源索引、混淆配置时使用** |

### 代码生成工程化治理红线 (CodeGen Governance)

代码生成是一把双刃剑：它简化了开发，但由于其“隐身”在编译过程中的特性，极易导致构建变慢和黑盒故障。

#### A. “KSP First” 治理准则
*   **红线：严禁在新模块中引入 KAPT，除非该依赖库尚未支持 KSP。**
*   **理由**：KAPT 会强制生成 Java Stub，即使在纯 Kotlin 项目中也会触发 Java 编译流程，导致增量编译退化。
*   **治理对策**：
    1. 优先使用支持 KSP 的库（如 Room, Glide, Moshi, Hilt/Dagger）。
    2. 逐步执行 **“KAPT-to-KSP 迁移计划”**，一旦项目清理掉最后一个 KAPT 依赖，编译速度将有质的飞跃。

#### B. 构建透明度与可见性
*   **准则**：生成的代码必须是 **“可观测”** 的。
*   **要求**：
    1. 严禁生成过于复杂的黑盒逻辑。生成的代码应遵循项目统一的代码风格。
    2. 开发人员必须知道生成代码的存放路径（通常在 `build/generated/ksp/...`），以便在排查问题时查看源码。
*   **调试建议**：在 KSP 插件中，应通过 `KSPLogger` 打印清晰的错误信息和源文件位置，防止编译报错时定位不到源头。

#### C. 增量构建红线 (Incremental Build)
*   **准则**：自定义 CodeGen 插件必须支持 **增量处理**。
*   **红线**：禁止编写非增量的 KSP 处理器（Aggregating vs Isolating 处理不当会导致全量重绘）。
*   **后果**：非增量的处理器会导致即使改动一行代码，Gradle 也会重新扫描全项目，破坏研发效率。

#### D. KMP 跨平台适配
*   **准则**：在 `shared` 模块中，禁止使用依赖 Java 环境的 CodeGen。
*   **方案**：
    *   使用 **Kotlinx.serialization** (编译器插件)。
    *   使用 **SQLDelight** (Gradle 插件预生成)。
    *   使用 **KSP** 编写跨平台代码生成逻辑。

### 代码生成选型决策路径

1.  **你需要处理自定义注解并生成一些类（如路由、自动注入）？**
    *   👉 **KSP + KotlinPoet**。这是目前的黄金组合。
2.  **你正在维护一个老旧项目，且大量使用 Dagger 2 或旧版 Room？**
    *   👉 继续使用 **KAPT**，但应优先评估这些库的 **KSP 版本** 并进行迁移。
3.  **你需要生成一些非代码类的资源（如：将 assets 下的文件名生成为枚举）？**
    *   👉 **Gradle Task + KotlinPoet**。无需复杂的符号处理，直接读文件生成即可。
4.  **你需要像 Kotlinx.serialization 一样，自动给类增加方法或接口？**
    *   👉 **Kotlin Compiler Plugin**。但请注意，它的 API 经常变动，且调试极其困难，除非你是资深架构师，否则慎入。
5.  **你希望根据 JSON 自动生成数据类？**
    *   👉 **IDE 插件 (如 Kotlin Data Class from JSON)** 或者 **Moshi 的 CodeGen 模式**。

### 总结意见：
在 Android 工程化中，**治理 KAPT 并转向 KSP** 是提升构建效率的单一最有效手段。将 CodeGen 纳入治理范畴，重点在于 **“管控增量编译”** 和 **“统一 KMP 适配路径”**。
