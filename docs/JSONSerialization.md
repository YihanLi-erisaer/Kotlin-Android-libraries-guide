### 序列化工程化治理红线 (Serialization Governance)

在架构设计中，序列化库的选型直接关系到数据的健壮性：

#### A. 空安全红线 (Null Safety Redline)
*   **准则**：**严禁在新项目中使用 Gson 处理 Kotlin Data Class**。
*   **理由**：Gson 在处理缺失字段时会直接注入 `null`，即使字段被声明为非空。这违背了 Kotlin 的类型系统，是线上 NPE 的头号杀手。
*   **治理要求**：新项目必须使用 **Moshi** 或 **Kotlinx.serialization**，它们在字段缺失时会抛出异常或使用默认值，确保数据的确定性。

#### B. 构建治理 (Build Engineering)
*   **准则**：优先使用 **KSP** 版本的 Moshi 或编译器插件版本的 Kotlinx.serialization。
*   **对策**：废弃所有基于 KAPT (Annotation Processor) 的序列化配置，以减少 15%-25% 的模块编译耗时。

#### C. Compose 稳定性治理
*   **背景**：Compose 编译器需要判断类是否不可变（Stable）。
*   **准则**：使用 **Kotlinx.serialization** 生成的 Data Class 默认对 Compose 友好。若使用 Moshi 或 Gson，需确保字段全部为 `val` 且不包含非稳定类型，否则会导致 Compose 频繁重组。

#### D. 混淆治理 (R8/Proguard)
*   **红线**：禁止通过反射访问未被 Keep 的字段。
*   **准则**：
    *   **Gson/Moshi**：必须为 Data Class 添加 `@Keep` 或在 Proguard 中保留，否则混淆后字段名改变导致解析失败。
    *   **Kotlinx.serialization**：由于不依赖反射，混淆治理最简单，只需保留编译器生成的 `Serializer` 类。

---

### 4. 总结：序列化选型决策路径

1.  **你是 Kotlin Multiplatform (KMP) 项目？**
    *   👉 **Kotlinx.serialization** (没有第二个选择)。
2.  **你是纯 Android Kotlin 项目，且重度使用 Retrofit？**
    *   👉 **Moshi + KSP** (性能与开发体验的平衡点)。
3.  **你是旧 Java 项目或需要与复杂 Java 库交互？**
    *   👉 **Gson** (但要小心 Kotlin 互操作)。
4.  **你需要处理海量数据或即时通讯？**
    *   👉 **Protobuf**。
