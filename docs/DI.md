### DI 治理红线与架构准则

#### A. 编译安全性红线 (Compile-time Safety)
*   **准则**：在超大型模块化项目中，优先选择具有 **编译期检查能力** 的 DI（如 Hilt 或 kotlin-inject）。
*   **痛点**：Koin 虽然开发快，但在大型项目中，如果漏写了一个 `module` 声明，只有在 App 运行到对应页面时才会闪退，这增加了 QA 测试的覆盖成本。

#### B. 构建性能治理 (Build Engineering)
*   **红线：严禁在所有模块无脑开启 KSP/KAPT**。
*   **治理对策**：
    *   如果使用 **Hilt**，必须严格按照官方推荐的“库模块不直接使用 Hilt”原则，尽可能通过接口抽象减少插桩范围。
    *   对于非核心业务模块，优先使用 **手动注入 (Manual DI)** 或 **Koin**，以换取秒级的增量编译体验。

#### C. Compose 集成准则
*   **原则**：ViewModel 的注入必须与 **Navigation BackStack** 绑定。
    *   使用 `hiltViewModel()` 或 `koinViewModel()` 时，应确保 ViewModel 的生命周期能随导航项正确销毁。
    *   **红线**：禁止在 Composable 函数内部通过 `get()` 或全局单例直接获取对象，这会破坏 Compose 的“预览能力（Preview）”和“单向数据流（UDF）”原则。

#### D. KMP 跨平台适配
*   **准则**：`shared` 模块的 DI 必须能够暴露给 iOS 端使用。
*   **最佳实践**：
    *   使用 **Koin** 作为跨平台“粘合剂”。
    *   在 iOS 端，利用 Kotlin 的 `inject` 属性委派或引入 **SKIE** 插件，使 Swift 代码能以更自然的方式访问 Shared 层的注入对象。

---

### 4. 总结：DI 选型决策决策路径

1.  **你是纯 Android 项目且追求稳定？** 
    *   👉 **Hilt**（没必要选别的，生态最全）。
2.  **你需要做 KMP（多端共享）？**
    *   追求开发速度 👉 **Koin**。
    *   追求极致性能和编译期报错 👉 **kotlin-inject**。
3.  **你是一个只有几个模块的小 App？**
    *   👉 **Koin**（无需配置插件，即加即用）。
4.  **你的项目模块超过 200 个，编译已经很慢了？**
    *   👉 尝试将业务模块从 Hilt 迁移到 **Koin** 或 **手动注入**。
