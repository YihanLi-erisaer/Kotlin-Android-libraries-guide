### 测试工程化治理红线 (Testing Governance)

测试不是为了覆盖率，而是为了“敢于重构”。建议增加以下治理准则：

#### A. 异步测试红线 (Async Testing Redline)
*   **准则**：严禁在测试中使用 `Thread.sleep()` 来等待异步结果。
*   **对策**：使用 **Turbine** 监听 Flow，或通过协程的 `runTest` 配合 `TestDispatcher` 进行时间跳跃（Virtual Time），确保测试既快又稳定。

#### B. UI 测试分层治理 (UI Testing Pyramid)
*   **红线**：禁止将所有 UI 验证都放在真机/模拟器（Espresso/Compose UI Test）上。
*   **策略**：
    1.  **逻辑验证**：放在 JUnit + MockK (JVM)。
    2.  **视觉验证**：放在 **Roborazzi** (JVM 截图)。
    3.  **核心路径交互验证**：少量放在 Compose UI Test (真机)。

#### C. Mock 治理准则
*   **准则**：禁止对 Data Class 进行 Mock。
*   **原则**：Mock 应该是为了解耦外部服务（如网络、数据库）。对于纯数据模型，应手动创建实例，以保证测试的真实性。

#### D. KMP 跨平台测试规范
*   **准则**：`shared` 模块的业务逻辑必须在 `commonTest` 中编写。
*   **要求**：使用 **kotlin.test** 的 API。这样一套测试用例可以同时在 JVM (JUnit) 和 iOS (XCTest) 上跑，确保双端逻辑 100% 对齐。

### 总结：测试选型决策路径

1.  **你是纯 Android 项目，需要测 ViewModel 逻辑？**
    *   👉 **JUnit 5 + MockK + Turbine**。
2.  **你的 Compose UI 经常被不经意的改动搞乱（视觉回归）？**
    *   👉 **Roborazzi** (截图测试)。相比跑真机，它能快 10 倍以上。
3.  **你需要测试 App 的冷启动优化效果？**
    *   👉 **Jetpack Macrobenchmark**。
4.  **你在做 KMP 跨平台？**
    *   👉 **kotlin.test** + **MOKO Resources (用于测资源加载)**。
5.  **你需要测试复杂的协程数据流（Flow）？**
    *   👉 **Turbine**。它能像流水线一样逐个 check Flow 发出的数据包。
