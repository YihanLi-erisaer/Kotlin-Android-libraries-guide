### 导航工程化治理红线 (Navigation Governance)

导航是 App 的“血管”，治理不好会导致参数丢失或内存泄露。建议增加以下准则：

#### A. 传递参数红线 (Argument Redline)
*   **红线**：禁止通过导航参数传递 **“大对象”**（如完整的 User 对象）。
*   **准则**：导航参数只应包含 **ID 或基本类型**。复杂对象应存储在 Repository 层或全局状态中，由目标页面根据 ID 自行拉取。
*   **理由**：导航参数会被序列化到 Bundle 中，大对象会导致 `TransactionTooLargeException` 并拖慢页面切换性能。

#### B. 类型安全治理 (Type-Safety Governance)
*   **准则**：严禁在项目中使用 **硬编码字符串路由** (如 `navController.navigate("detail/123")`)。
*   **治理要求**：
    *   **官方库**：必须使用 `@Serializable` 对象。
    *   **Voyager**：使用 `Screen` 类定义。

#### C. 深链接治理 (Deep Link Governance)
*   **准则**：所有页面跳转逻辑必须具备 **“可唤起性”**。
*   **要求**：在设计导航结构时，需提前规划深链接路径，确保外部 App 或 H5 能够精准定位到二级、三级页面。

#### D. 多堆栈治理 (Multi-Stack Strategy)
*   **准则**：在主界面（Bottom Navigation）场景下，必须处理好 **“状态保留与恢复”**。
*   **要求**：使用官方库时，必须配置 `saveState = true` 和 `restoreState = true`，防止切换 Tab 时页面状态丢失。

### 总结：导航选型决策路径

1.  **你是纯 Android 项目，且追求长期稳定性？**
    *   👉 **Navigation Compose 2.8.0+**。官方类型安全已足够好用，深链接处理最完善。
2.  **你需要做跨平台 (KMP)，且希望像写 Compose 一样简单？**
    *   👉 **Voyager**。它的 Screen 模型非常直观，适合快速交付。
3.  **你的项目极其庞大，且需要实现复杂的逻辑解耦（如逻辑层完全不依赖 Compose）？**
    *   👉 **Decompose**。它是目前唯一能真正实现逻辑组件独立于 UI 运行的方案。
4.  **你还在用 Fragment，但想逐步过渡？**
    *   👉 继续使用 **Navigation (Fragment)**，它是目前兼容 View 和 Compose 混合开发的桥梁。
